# 0016. OAuth 2.1 sign-in for MCP clients

Status: Accepted

## Context
ADR 0015 made `/mcp` available with API tokens (ADR 0014). Claude Code, Gemini CLI and Cursor can send a token header, but ChatGPT custom connectors and Claude's "Add custom connector" cannot: they connect by address and expect the MCP authorization flow (OAuth 2.1 with PKCE, protected resource metadata, authorization server metadata, dynamic client registration, resource indicators). That flow adds public endpoints, a credential type with a refresh loop and a page where people approve strangers' software, so the maintainer rule is: optional, off by default, and invisible while off.

## Decision
- **Switch:** the instance setting `oauth_enabled` (default `false`, also when hosted; `GET/PATCH /api/v1/admin/settings` as `oauthEnabled`, admin page, with an explanation). It can be enabled only when `GUNKLY_BASE_URL` is `https://` or `http://localhost`/`127.0.0.1`/`[::1]` (development and the e2e server): otherwise `400 oauth_requires_https`. It is also effective only while `mcp_enabled` is on and the base URL still qualifies, so a later config change cannot leave OAuth half on. The check is one cached read (`features`, shared with `mcp_enabled`).
- **Off means absent:** every route below is registered but carries the policy flag `oauthOnly`; the router answers `404` before CSRF, rate limits or any body is looked at. The `/mcp` challenge stays plain `Bearer`, `GET /api/v1/instance` omits `oauthEnabled`, access tokens are an unknown credential (`401`). Existing grants are dormant, not deleted, and live again if the admin turns it back on.
- **Endpoints**, documented under `x-outside-api-v1`, each with an explicit policy that registration validates: `GET /.well-known/oauth-protected-resource` (and `/mcp` suffixed, RFC 9728), `GET /.well-known/oauth-authorization-server` (RFC 8414; issuer = base URL; `S256` only; `token_endpoint_auth_methods` `none`; `authorization_response_iss_parameter_supported`), `POST /oauth/register` (RFC 7591), `GET`/`POST /oauth/authorize`, `POST /oauth/token`, `POST /oauth/revoke` (RFC 7009). When on, `/mcp` 401 responses carry `Bearer resource_metadata="<base>/.well-known/oauth-protected-resource"`.
- **Public clients only.** No client secrets: a secret in an anonymously registered client proves nothing, and PKCE is what binds the flow. A registration that asks for `client_secret_*` is told it got `none` (RFC 7591 allows the server to substitute). No CORS headers: the clients we target call from servers or native apps; browser-based clients are not supported.
- **Dynamic registration** is open (the protocol needs it), so everything about a client is treated as attacker-chosen. Redirect URIs: 1 to 5, https, or http on a loopback host (any port at run time, RFC 8252), no fragment, userinfo, wildcard, control or non-ASCII characters (IDN in punycode only), a valid port; authorization matches them exactly (loopback: any port). The validator is fuzzed (`FuzzValidRedirectURI`). `client_name` is at most 100 characters without control characters. `client_name` may not contain "gunkly" once folded (NFKD, combining marks dropped, lower case: fullwidth, styled and accented lookalikes included), so an app cannot pass for Gunkly itself. Limits through `internal/limits`: `oauth_clients` (instance-wide, default 1000), `oauth_unused_clients_per_ip` (clients with no approved grant per registering address, IPv6 as its /64, default 20, then `503`) and a per-IP rate bucket (10/min). The registering address key is stored with the client (`reg_key`, migration 0014) only to count that cap; it is never logged. A client counts as used only when a user approves it (a grant is created) or a token is issued, never when someone merely opens the consent page; clients never used within **one hour**, and idle ones without grants after 90 days, are purged by the retention job. At the instance cap, registration evicts the oldest unused client instead of failing, and fails only when every client is in use, so a flood of registrations cannot lock real apps out.
- **Authorization:** `GET` validates `client_id` and `redirect_uri` first and answers a bad pair with an error page (never a redirect); other faults (`invalid_request`, `unsupported_response_type`, `invalid_scope`, `invalid_target`) redirect with `state` and `iss`. Required: `response_type=code`, `code_challenge` (43 base64url characters) with `code_challenge_method=S256`; `resource`, when given, must equal `<base>/mcp`; `scope`, when given, a subset of the three scopes. A signed-out user is sent to `/signin?next=...` (the SPA does a full page load back to `/oauth/...`). The consent page is server-rendered `html/template` with no script, the text through `internal/i18n`, the done-page stylesheet, light and dark: the app name (escaped) and an **Unverified app** notice, the host it will return to, the host it will return to as the most prominent line ("You'll be sent back to:" in large text) above the notice, an extra warning when this user has never approved an app returning to that host, checkboxes for households (all, with the user's role; guests are read only whatever is ticked) and actions (read always; complete preselected; create preselected only if the app asked for it by name), Allow and Deny. The post is CSRF-protected with the cookie token as a hidden field plus the cross-site check (`policy.formCSRF`), re-validates every hidden field (they are client-controlled), and answers `303` to the redirect URI with `code`, `state`, `iss` (or `error=access_denied`). Browsers check `form-action` against that redirect, so this page alone gets `form-action 'self' <origin of the matched redirect URI>` (frame-ancestors stays `'none'`). A hosted account must pass the same email/2FA gate as token creation.
- **Step-up on consent:** approving needs a recent step-up, as creating an API token does. When the session's `step_up_at` is unset or older than 15 minutes the consent form carries a password field (`autocomplete="current-password"`), a code field when the account has an authenticator app (`one-time-code`; six digits are an authenticator or emailed code, anything else a recovery code) and, for accounts with email codes, an "Email me a code" button that sends the code through the same path and limits as `POST /api/v1/session/step-up` and re-renders the form with the code field. The post is verified server-side with the same password and second-factor verifiers, the same per-account backoff (`acctGuard`, keys shared with the REST step-up) and per-IP/account rate bucket (a throttled post answers a `429` page), and failures are audited as `login_failure` (`via` `oauth_consent`). Wrong or missing credentials re-render the form with one generic message (no oracle for which part was wrong). Success sets `step_up_at` and continues; within the window the form has no extra fields. Deny never needs a password. The page stays script-free and style-free; the text is in `internal/i18n`.
- **Grant and tokens:** a grant (user, client, scopes, households, absolute 90-day lifetime) is created with the code and becomes active when the code is redeemed (unredeemed grants are purged after an hour). Codes: `ids.Token()`, SHA-256 at rest, 60 s, single use. Access tokens `gko_` + 43 characters, one hour; refresh tokens `gkr_` + 43, rotated on every use, 30 days idle, never beyond the grant. Both are stored hashed in `oauth_tokens`. A used code or rotated refresh token presented again revokes the grant (audited `oauth_token_reuse`); a code is spent by the first attempt even when PKCE or the redirect then fails, so an intercepted code cannot be probed. Refresh ignores a `scope` parameter and returns the grant's scopes. Token responses are `Cache-Control: no-store`; errors are RFC 6749 JSON.
- **Use:** an access token authenticates `/mcp` only (`authenticateBearer` accepts `gko_` only for `authMCP` routes): on the REST API it is an unknown credential. On `/mcp` it becomes the same `store.APIToken` description API tokens produce (its id is the grant id; scopes, bound households that the owner still belongs to, the owner's live role per call, the same per-token and per-IP rate limits, the same `tools/list` filtering). The audience is a single fixed resource, so the resource indicator is checked at authorize and token time rather than stored.
- **Attribution:** completions made with an OAuth access token are recorded with their own source `oauth` and `token_id` = the grant id (audited `token_complete` with `token` = the grant id), so they cannot pass for API token completions. Migration 0014 widens the `completions.source` `CHECK` (a table rebuild on SQLite that keeps rows, indexes, foreign keys and `undo_tokens`; `DROP`/`ADD CONSTRAINT` on Postgres). Chore history (`GET .../completions`) returns `via`, the connected app's name, for these (the history label shows it, or "Connected app" once the grant has been purged); the export writes the stored source and the import validator accepts `oauth` (the format version is unchanged; imports still record their history as `import`).
- **Revocation and lifecycle:** Account, Integrations, **Connected apps** (`GET /api/v1/account/oauth-grants`, `DELETE /api/v1/account/oauth-grants/{id}`; session only, not gated so a user can clean up while OAuth is off) disconnects a grant; `POST /oauth/revoke` revokes the grant of an access or refresh token issued to the calling client and always answers 200. A password change or reset, removal of a second factor (via the hook that revokes API tokens), account deletion, and leaving a household (the binding is dropped, rejoining does not revive it) apply as for API tokens. Audit events: `oauth_grant`, `oauth_token_reuse`, `oauth_revoke`.
- **Storage:** migration 0013: `oauth_clients`, `oauth_grants`, `oauth_grant_households`, `oauth_codes`, `oauth_tokens`; timestamps in Unix milliseconds; SQLite and Postgres; the daily retention job deletes expired codes and tokens, revoked, expired and unredeemed grants and unused clients.
- **Dependencies:** none new. The SDK's `auth` and `oauthex` packages were considered and not used: they provide a bearer-token verifier and metadata types for a resource server, while our authentication, rate limiting and tenancy checks run in the router and the store before the SDK sees the request, and the authorization server (which the SDK does not provide) is the larger part.

## Threat analysis
- **Open registration phishing** (an app calling itself "Gunkly Backup"): labelled unverified on every consent page, name escaped, the real return host shown, exact redirect matching, a signed-in user in the loop, least-privilege defaults, per-user grant cap, everything revocable and audited. The residual risk is a user approving a lookalike (with their password just typed); the page says what is being granted and to which host, and the grant never exceeds the user's own role.
- **Code interception / injection:** PKCE S256 only, single-use 60-second codes bound to client, redirect URI and challenge, reuse revokes, `iss` on the redirect.
- **Token theft:** one-hour access tokens usable on `/mcp` only; rotating refresh tokens whose reuse (by thief or owner) kills the grant; revocation by the user at once.
- **Mix-up and confused deputy:** the resource indicator must be this instance's `/mcp`; the issuer is returned (`iss`); the token is accepted nowhere else.
- **Session hijack:** consent needs a step-up (password, and the second factor when set, within 15 minutes), verified on the server with the usual backoff, so a stolen session cookie alone cannot approve an attacker's app. The grant is also visible under Connected apps, audited and revocable, and a password change revokes it.
- **Registration exhaustion:** unused clients live one hour, one address can hold only 20 of them, and at the instance cap the oldest unused client is evicted rather than refusing everyone; only clients a user approved are safe from eviction.
- **Impersonating Gunkly:** names containing "gunkly" (folded) are refused at registration; the return host is the largest line of the consent page and a first-time host carries its own warning.
- **Browser-based clients:** no CORS headers are sent anywhere, so a web page cannot call the registration, token or revocation endpoints from a browser. Browser-based (CORS) MCP clients are not supported; clients must be servers or native apps. Supporting them would mean allowing cross-origin calls to endpoints that anonymous callers can reach, which is a decision for its own ADR.
- **CSRF / clickjacking:** form token plus cross-site check; `frame-ancestors 'none'`; no script.
- **Enumeration and abuse:** metadata is public by definition; the token and revocation endpoints answer uniformly (`invalid_grant`, always `200`), and per-IP buckets apply.

## Consequences
- Another credential type and about 900 lines of Go, a migration and a consent page to maintain; all of it dormant unless an admin opts in.
- Sign-in with a hosted-mode account that lacks a verified address or second factor is refused at the consent page, as for API tokens.
- Browser-based MCP clients (which need CORS) and confidential clients are not supported (see the threat analysis); both can be added later without changing the stored model.
- The web bundle grew about 1.4 KB gzipped (Connected apps, the two guide options, an admin switch); the total stays under the 100 KB budget, partly by replacing the audit-event label list with a dictionary lookup.
