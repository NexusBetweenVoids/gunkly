# 0017. Outgoing webhooks

Status: Accepted

## Context
Home automation and scripts want to react to what happens to a chore (completed, overdue, ...) without polling. Notification channels (ADR 0007) send human text through Shoutrrr; they are the wrong tool for machine-readable, signed events. A webhook makes Gunkly call a URL a household owner chose, which is the SSRF surface ADR 0006 exists for, plus a new stored secret, a retry queue and a log. The maintainer rule is the one OAuth followed (ADR 0016): optional, off by default, invisible while off.

## Decision
- **Switch:** the instance setting `webhooks_enabled` (default `false`, also when hosted; `GET/PATCH /api/v1/admin/settings` as `webhooksEnabled`). While off every webhook route answers `404` (policy flag `webhooksOnly`, checked by the router before anything else, one cached read shared with the MCP and OAuth flags), `GET /api/v1/instance` omits `webhooksEnabled`, the store queues nothing (one settings read per chore event) and the scheduler sends nothing and drops pending deliveries. Existing webhooks are dormant, not deleted.
- **Who:** household **owners** only, for every route (list, create, change, delete, rotate, test, log). Never API tokens (`noToken`). Creating, changing (including switching on or off) and rotating the secret of a webhook need a step-up, since a changed address would receive every signed event. Limit `webhooks_per_household` (default 10) through `internal/limits`, counted in the creating transaction. Migration 0015 adds `webhooks` and `webhook_deliveries` (both cascade with the household).
- **Targets:** `https` only. With the egress guard off (self-hosters reaching their LAN) `http` is allowed too. No userinfo, fragment, whitespace, control or non-ASCII characters (IDN in punycode), at most 2048 characters, a valid port. While guarded, literal blocked IPs, `localhost`, `*.localhost`, `*.local`, `*.internal` and hosts whose last label is numeric or hex (ambiguous IPv4 spellings) are rejected at save time for a clear error; this is a convenience only. The authority is the dial hook, which checks the address actually connected to (ADR 0006), and a stored URL is validated again at send time against the guard setting then in force, so turning the guard on later also stops existing loopback targets. The validator is fuzzed (`FuzzValidateURL`). The guard is **mandatory** for every send, tests included; hosted mode forces it on.
- **Secrets at rest:** the URL (it often carries a token) and the signing secret are sealed with `auth.Keyring`, associated data `webhook-url:<id>` and `webhook:<id>`, and covered by `gunkly rotate-key`. Lists show only the host. The secret (`whsec_` and 256 random bits) is returned once, on creation and on rotation (`POST .../rotate-secret`; the old one stops signing at once).
- **Events:** `chore.completed`, `chore.completion_reverted`, `chore.overdue`, `chore.created`, `chore.updated`, `chore.deleted`, `chore.snoozed`, `chore.skipped`, plus `ping` for the test button. A webhook subscribes to a non-empty subset.
- **Payload** (stable, `version` 1): `{"id","type","version","createdAt","householdId","data":{"chore":{id,name,dueDate,assignees:[ids]},"completion"?:{id,completedAt,source,revertedAt?},"actor"?:{id,displayName}}}`. No secrets, no email addresses, no notes, no links. The chore is the state after the event (`chore.deleted`: as it was). `actor` is absent for the scheduler and for mark-done links of a household channel. Additive changes keep the version; a breaking change adds a new version.
- **Outbox:** an event writes its deliveries in the transaction of the change that caused it (`emitWebhook` inside the store methods), so an event is queued exactly when it happened and never when it rolled back. Delivery rows carry the finished payload and a unique key `<webhook id>:<event id>`: a repeated event is a no-op. `chore.overdue` is produced by the scheduler when a chore's due date ends (local midnight after it in the household zone); its event id derives from chore and due date, so restarts, a second instance or an overlapping window never queue it twice. At most 1000 pending deliveries per webhook; further events are dropped.
- **Sending:** the scheduler (the same leader that sends reminders) claims due deliveries with a lease (`FOR UPDATE SKIP LOCKED` on Postgres) and posts through the guarded client with `Redirect` disabled (a 3xx is a failed delivery, never followed), a 15 s timeout, and the response body read up to 4 KiB and thrown away. Headers: `Content-Type: application/json`, `User-Agent: Gunkly-Webhook/<version>`, `Gunkly-Event`, `Gunkly-Delivery` (the delivery id, identical on retries), `Gunkly-Signature: t=<unix>,v1=<hex HMAC-SHA256 of "<t>.<body>" keyed with the secret>`. The signature is recomputed on every attempt, so the timestamp is fresh; receivers should reject timestamps more than 5 minutes off (replay window) and may de-duplicate on `Gunkly-Delivery` or the payload `id`.
- **Retries:** 2xx is success. 5xx, 408, 425, 429 and network errors retry with the reminder backoff (1, 2, 4, 8, 16 minutes, then give up: 6 attempts). Other 4xx, 3xx and blocked or invalid targets fail at once. **Auto-disable:** every failed attempt counts; 20 consecutive failures (any success resets) switch the webhook off, fail its pending deliveries, write the audit event `webhook_auto_disable` and show a notice in the UI (`autoDisabled`); turning it back on clears the count.
- **Log:** the last 50 attempts per webhook (status, HTTP code, duration, error), pruned on write and with the delivery retention setting. Errors are fixed categories ("HTTP 503", "timed out", "connection failed", "destination address not allowed"), never the URL, an address or response text. The test button sends a signed `ping` synchronously, logs it like a delivery, is rate limited per user, is not retried and does not count towards the switch-off.
- **UI:** Household settings, owners only, a collapsed "Webhooks (advanced)" section in a lazy chunk, present only while the instance setting is on: list, add (URL, event checkboxes, description), the secret once with copy and a short verification snippet, test, log, turn on/off, new secret, delete.

## Consequences
- One more stored secret and an outbound path, both off by default; no new dependency.
- Delivery is at least once per event while the instance is up; ordering is not guaranteed across retries. A receiver that needs exactly-once de-duplicates on the event id.
- **Export/import (0.5.1, replaces "not part of the export"):** an owner's household export carries an optional `webhooks` array (name = description, events, URL, enabled). The signing secret is never exported (the store query does not even select it) and the URL is decrypted only for the owner's export, so the file is sensitive (documented in `docs/webhooks.md`, the README and OpenAPI). A member's export has none. The format stays version 1: the field is additive and omitted when empty, like `rotation`; an older build rejects a file that has it (strict schema), a newer build reads old files unchanged. Import (new household, or merge by an owner) re-creates every webhook **disabled** with a fresh sealed secret, because a target is a per-instance decision and nothing should be delivered to an old endpoint unreviewed; the owner rotates the secret (shown once) and enables it through the existing flow. Import respects the `webhooks_enabled` instance switch (off: all skipped), the importer's role (members skip), `webhooks_per_household` (checked in the same transaction) and the URL rules in force now (`webhook.Prepare`, egress guard); a skipped entry is reported as `webhooksSkipped` with a reason, never fails the import. Audit metadata of the export and import carries the webhook count.
- Hosted: the same guard, limits and 404-while-off apply; the operator decides whether to enable it.
