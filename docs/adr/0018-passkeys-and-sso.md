# 0018. Passkeys and single sign-on

Status: Accepted

## Context
Passwords plus TOTP or emailed codes (ADR 0008, 0013) leave two gaps for 0.5: people want to sign in without typing a password (passkeys), and self-hosters who already run an identity provider (Authelia, Authentik, Keycloak, Kanidm, Zitadel, Pocket ID, Google) want one sign-in for everything (SSO). Both are optional, both touch the most security-sensitive code in the app, and the hosted service must stay as strict as before.

Two dependencies were approved for this work: `github.com/go-webauthn/webauthn` (WebAuthn ceremonies, attestation and assertion verification, COSE keys) and `github.com/coreos/go-oidc/v3` (OpenID Connect discovery, JWKS caching and ID token verification). Both are small, widely used and the part of the problem where hand-written code is most likely to be wrong. `golang.org/x/oauth2` (already in the module graph through the MCP SDK) becomes a direct dependency for the authorization-code exchange with PKCE. The Go dependency budget (10) was not raised: the app has 9 direct requirements.

## Decision: passkeys

**What a passkey is here.** A WebAuthn credential of one account, stored as public material only: credential ID, COSE public key, signature counter, transports, AAGUID and the authenticator flags (migration 0019, `passkeys`). The private key never leaves the user's device. Attestation is `none`: Gunkly never asks which device made a key, so it needs no certificate store or metadata service. Registration requires a discoverable credential with user verification, which is what lets a passkey sign in without a username.

**Three uses.**
1. *Passwordless sign-in* ("Sign in with a passkey" on the sign-in page): a discoverable-credential assertion with user verification required (PIN, fingerprint or face on the device). Possession plus verification count as password plus second factor, so this satisfies the hosted mandatory-2FA rule.
2. *Second factor after a password*, alongside TOTP and emailed codes. The sign-in answer names the options (`method`, and `passkey: true` when the account has a passkey and passkeys are available). An account that has passkeys is asked for a second factor at password sign-in even if it has no TOTP or email codes: a passkey is a second factor, not just a login shortcut. User verification is `preferred` here, because possession is what this factor proves.
3. *Step-up.* A user-verified passkey alone re-verifies a session (`POST /session/step-up` with `passkey`), as password plus second factor would. Registering and removing passkeys need step-up.

**Relying party.** The RP ID is the host of `GUNKLY_BASE_URL` (no port) and the only allowed origin is its origin. Passkeys work only with an `https` base URL or `http://localhost`, and never with an IP address (not a valid RP ID); otherwise `GET /api/v1/instance` reports `passkeysAvailable: false`, the sign-in options endpoints answer 404 and registration answers `400 passkeys_require_https`, and the account screen explains why. Changing the base URL host later orphans existing passkeys (the browser will not offer them); recovery codes and the other factors still work.

**Ceremony state.** Each ceremony is two calls. "Options" stores the library's session data (challenge, allowed credentials, user-verification rule) in `passkey_challenges` for five minutes under a random ID (only its SHA-256 is stored), bound to a purpose (`register`, `login`, `second`, `stepup`) and to the account; "finish" takes and deletes the row in one transaction, so a challenge works once and a failed attempt spends it. State lives in the database, not in memory, so it works behind several instances. Expired rows are deleted when a challenge is saved and by the daily retention job. A ceremony started for one account or purpose is useless for another.

**Sign counter.** After a verified assertion the counter is stored with a conditional update (`sign_count < new`, or both zero for authenticators that never count, as synced passkeys do). A counter that did not increase means a cloned authenticator or a replay: the sign-in is refused (`401 invalid_passkey`), a warning is logged (user and passkey IDs, never the credential) and a `login_failure` audit event with `reason: passkey_sign_count` goes to the account's log.

**Limits and rate limits.** `passkeys_per_user` (default 20) in `internal/limits`. The ceremony endpoints that work without a session (`/session/passkey/*`) have their own per-IP bucket (`passkey`, 20 per minute); the second-factor options endpoint verifies the password first, with the usual per-login bucket and per-account backoff, so it reveals nothing about accounts it has not authenticated. Failed second-factor and step-up assertions count against the same per-account backoff as TOTP codes. Registration endpoints share the `passkey` bucket (a registration is several calls and the generic 2FA bucket is 5 per minute).

**Credential changes.** Adding a passkey signs out the account's other sessions, like enabling TOTP. Removing one signs out the other sessions and revokes API tokens and OAuth grants, like removing another second factor (audit `token_revoke` with `via: passkey_remove`). The first second factor of an account (no TOTP, no email codes, no passkey yet) also issues recovery codes, shown once, so losing the only passkey is recoverable; turning TOTP or email codes off keeps the recovery codes while a passkey remains, and removing the last second factor deletes them. In hosted mode the last second factor cannot be removed (`409 two_factor_mandatory`). `gunkly admin reset-2fa` removes passkeys too (an admin who is locked out of nothing else should not leave a passkey that still signs the user in). Account deletion deletes passkeys and challenges. The personal data export lists passkey names and dates, never key material.

**Front end.** `navigator.credentials` is used directly, with small base64url helpers (`web/src/lib/passkey.ts`), loaded with a dynamic import by the screens that need it, so the initial bundle did not grow. No npm dependency was added. All text is in the translation files.

## Decision: SSO

**Scope.** OpenID Connect sign-in for self-hosted instances. Configured by `GUNKLY_OIDC_ISSUER`, `_CLIENT_ID`, `_CLIENT_SECRET` (optional: a public client), `_NAME` (button label) and `_SCOPES` (default `openid profile email`). Config loading refuses these in hosted mode, and the server also ignores them there; every SSO route carries the policy flag `ssoOnly`, so it answers 404 when SSO is not configured or in hosted mode, before anything else is looked at. `GET /api/v1/instance` advertises `sso: {name}` only while on. There is no "SSO only" switch: password sign-in stays.

**Flow.** Authorization code with PKCE (`S256`), `state` and `nonce`. The redirect URI is `{BASE_URL}/api/v1/auth/oidc/callback`; the base URL must be https or localhost (checked at start-up). Discovery, JWKS caching and ID token verification (signature with the algorithms the provider advertises, which go-oidc narrows to RS/PS/ES/EdDSA and never `none` or HMAC, so Kanidm's ES256 works; issuer, audience, `azp` when there are several audiences, expiry, nonce) use `go-oidc`; the code exchange uses `golang.org/x/oauth2`. The `iss` response parameter (RFC 9207) is checked when present. Discovery is lazy and retried at most every 15 seconds, so a provider that starts after Gunkly, or is down, only affects the SSO button (the sign-in page then says "unavailable"). The token endpoint authentication method follows the provider's discovery (basic, form post, or auto-detection).

**Flow state** is a sealed cookie (`gunkly_sso`, key ring AEAD, HttpOnly, `SameSite=Lax`, path `/api/v1/auth/oidc`, 10 minutes, cleared on first use) holding state, nonce, verifier, the mode and, for link and step-up, the user and session. It ties the flow to the browser that started it (login CSRF) and needs no server state, so it works behind several instances. The callback always ends in a 303 redirect to the app with a result code (`?sso=failed|denied|unavailable|no_account|already_linked|linked|stepup`), never an error page; details go to the log, never tokens.

**Identity.** The key is `(issuer, sub)` (`sso_identities`, migration 0020; unique on that pair and on `(user, issuer)`), never an email or username. **No auto-linking by email, ever:** a provider that lets users pick any address would otherwise be a takeover path.
- *Linking* is started from Account, Sign-in & security with step-up, and completes only for the same signed-in session (and a still-valid step-up). It signs the account's other sessions out, like adding another way in.
- *Unlinking* needs step-up and is refused (`409 sso_last_login`) while the account has neither a password nor a passkey; it signs out other sessions and revokes API tokens.
- *First sign-in by an unknown identity:* the instance setting `sso_create_accounts` ("Create accounts for new single sign-on users", Administration, Sign-up & sign-in; **default off**). Off: the sign-in ends on a friendly "no account linked" message. On: an account is created with a username from `preferred_username` (reduced to the characters usernames allow, at most 28 long, de-duplicated with `-2`, `-3`, ... and finally a random suffix), the display name from `name`, no password (`password_hash` is the marker `!sso`, which never verifies; a login for such an account does the same work as a wrong password), and the email address **only** if `email_verified` is true, email is enabled here and the address is free; then it counts as verified. A concurrent first sign-in of the same subject ends up in the same account.
- Account deletion deletes identities; the data export says whether SSO is linked.

**Second factor.** An SSO sign-in counts as fully authenticated: the provider is responsible for multi-factor. Gunkly asks for no TOTP, email code or passkey after it. This is a deliberate trade-off (documented in `docs/sso.md`); an administrator who wants MFA must require it at the provider.

**Step-up for accounts without a password.** Sensitive actions need step-up (ADR 0013). A user linked to SSO can re-verify through the provider (`POST /session/step-up/sso`), which is asked to authenticate the user again (`prompt=login`, `max_age=0`); the callback checks that the identity is the account's own and, if the ID token carries `auth_time`, that it is under five minutes old. A provider that ignores both parameters and sends no `auth_time` makes this as weak as its own session; this is documented. The account can then set a password (the password change needs only step-up).

**The identity provider client and the egress guard.** Self-hosted providers sit on the LAN, which the egress guard (ADR 0006) blocks. Requests to the **issuer's own host and port** therefore skip the private-address block; the address comes from the environment the operator controls, not from user input. That client (`egress.NewIdPClient`) follows **no redirects** (a 3xx is an error, never a hop to another host), has dial, header and total timeouts and caps response bodies at 1 MiB, and ignores proxy variables. Any other host that the discovery document names (a token or key endpoint elsewhere, such as Google's) is dialled through the guard as usual (and so is subject to the admin's egress setting), so a hostile discovery document cannot aim the server at the internal network. `TestSSOGuardsOtherHostsInDiscovery` and the egress tests pin this.

**Rate limits.** The start, callback, link and step-up routes share the per-IP bucket `sso` (20 per minute). Nothing about SSO is guessable by password, so the per-account backoff does not apply.

**Limits.** An account has at most one identity per issuer and one issuer is configured, so identities are bounded by the number of accounts and need no entry in `internal/limits`.

## Dependencies
`go-webauthn/webauthn` v0.18.2 and `coreos/go-oidc/v3` v3.21.0 (with their transitive modules, among them `go-jose`, `fxamacker/cbor`, `go-tpm` and `x/oauth2`, now a direct requirement). The direct Go requirements went from 6 to 9 (budget 10, not raised). Together they grew the stripped binary from 25.7 MB to 29.2 MB (+3.4 MB, about 13%; `go-webauthn` brings CBOR, COSE and TPM attestation parsing even though attestation is `none`), and the web bundle by about 0.5 KB gzipped (the passkey code is loaded on demand). The same change moved the indirect `gorilla/websocket` (pulled in by Shoutrrr) to the commit that fixes GO-2026-6278, which `govulncheck` reported.

## Consequences
- The OAuth consent page (ADR 0016) is script-free and cannot run a WebAuthn ceremony: an account whose only second factor is a passkey types a recovery code there next to its password, and an account without a password (created by SSO) cannot approve an app until it sets one.
- Single sign-on adds a trust relationship: whoever controls the provider's account for a linked `sub` controls the Gunkly account. Keep the provider's own sign-in strong; unlink and password reset remain under Gunkly's control.
- An account created by SSO has no password until it sets one, so it is recoverable only through the provider (or an administrator's `reset-password`).
- Accounts with a passkey are asked for it at every password sign-in. That is intended (it is a second factor) and the recovery codes are the way back if the passkey is lost.
- Passkeys tie the instance to its base URL host. This is inherent to WebAuthn.
- The sign-count check rejects authenticators that go backwards; synced passkeys that always report 0 are accepted.
