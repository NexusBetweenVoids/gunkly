# Gunkly Threat Model

Covers self-hosted and the hosted service. Hosting infrastructure (servers, networking) is out of scope here.

## Assets

| Asset | Why it matters |
|-|-|
| Household content (chores, notes, history) | Private home information; tenant isolation is the core guarantee |
| Credentials: password hashes, TOTP secrets, recovery codes, sessions, API tokens | Account takeover |
| Notification URLs (bot tokens, webhook secrets) and VAPID private keys | Allow impersonation and spam via the user's channels |
| Outgoing webhook URLs and signing secrets | The URL may carry a token; the secret lets anyone forge events to the receiver |
| Mark-done tokens and calendar feed tokens | Unauthenticated capabilities |
| Instance secret key | Decrypts stored secrets |
| Email addresses and display names | Personal data (GDPR) |
| Instance IP and SMTP reputation | Abuse would break delivery for everyone |
| Backups | Contain all of the above |

## Actors

| Actor | Capabilities / intent |
|-|-|
| Anonymous internet | Probes endpoints, sign-up, login, tokens; credential stuffing; spam sign-ups |
| Malicious user / tenant | Valid account; tries ID guessing, cross-household access, SSRF through notification URLs, abuse as spam relay |
| Curious instance admin | Admin panel and DB/host access; should not read household content through the app |
| Compromised notification provider | Sees reminder text and mark-done links sent to it |
| Link-preview bots and mail scanners | Fetch every link automatically |
| Malicious self-hosted service URL | User-supplied endpoint (webhook, ntfy, Gotify) that redirects or returns data to reach internal addresses |

## Trust boundaries

1. Internet to Gunkly (reverse proxy, then app). Client IP trusted only from configured trusted proxies.
2. Browser/API client to server: sessions with CSRF protection, or scoped API tokens.
3. Handlers to data: only through `internal/store`, which enforces household membership and role (ADR 0009).
4. Gunkly to outbound services (Shoutrrr targets, Web Push endpoints, SMTP, update check): crosses to untrusted networks, passes the egress guard (ADR 0006).
5. Third-party relays: Discord, Telegram, Slack, Apple, Google, Mozilla and Microsoft push services receive reminder text or push metadata outside Gunkly's control and, for hosted, outside the EU. Treated as untrusted; mark-done links are single-use and short-lived because they traverse these channels.
6. Email: email-OTP 2FA shares a trust boundary with email-based password reset and verification links. An attacker controlling the mailbox can do all of them (a reset still leaves the second factor in place, but with email-OTP the mailbox is that factor), so email-OTP defends against password reuse and credential stuffing but not mailbox takeover. TOTP is the stronger second factor. Outbound SMTP crosses boundary 4: it dials through the egress guard, so a hosted instance needs a public relay.
7. Operator vs tenant: instance admin is trusted with the instance, not with household content in-app; DB and host access can read data, so secrets are encrypted at rest and operators are in the trust base.

## Threats and mitigations

| Threat | Mitigation (plan section) |
|-|-|
| Cross-household read/write, ID guessing | Single scoped data-access layer, membership checked in-query, UUIDv7 public IDs, parameterised isolation tests per endpoint, depguard + fitness tests (Tenant isolation) |
| Password guessing, credential stuffing | Argon2id, per-IP (IPv6 by /64) and per-IP+account rate limits with exponential backoff, per-account failure backoff across IPs, fail-closed limiter table, no hard lockout, no implicit step-up at sign-in, mandatory 2FA on hosted (Authentication) |
| Passkey cloning or replay, phishing | WebAuthn binds each assertion to the RP ID and origin of `GUNKLY_BASE_URL`; challenges are random, single use, expire in 5 minutes and are bound to the account and purpose; passwordless sign-in requires user verification; a signature counter that does not increase is refused and audited; only public keys are stored; per-IP buckets and the per-account backoff apply (ADR 0018) |
| SSO login CSRF, code injection, token forgery, mix-up | `state` and `nonce` in a sealed single-use cookie bound to the browser, PKCE S256, ID token signature, issuer, audience, `azp` and expiry verified (go-oidc), `iss` response parameter checked, callback always redirects with a short code; identity is `(issuer, sub)` and never matched by email (ADR 0018) |
| SSRF through the SSO provider's discovery document | Only the configured issuer's own host and port may skip the private-address block; every other host it names is dialled through the egress guard; no redirects, timeouts, 1 MiB response cap |
| Session theft / CSRF | Secure httpOnly SameSite cookies, CSRF protection, revocable sessions, 15-minute step-up for sensitive actions, strict CSP (Authentication, Web hardening) |
| Stolen API token | `gk_` + 256 random bits, SHA-256 hash at rest, shown once, revocable at once, optional expiry, household-bound, least-privilege scopes without implication between them, effective permission = scope AND the owner's current role (a guest owner reads only; a demotion or leaving applies immediately, and leaving deletes the household binding so rejoining does not revive it), revoked with the account's sessions on password change or reset and when a second factor is removed, never able to reach account, sessions, 2FA, members, settings, channels, export/import, admin or token management (an explicit `withToken`/`noToken` declaration per route, enforced at registration and by a route-table test, ADR 0014); per-token and per-IP rate limits (JSON-RPC batches on `/mcp` are refused so one request is one call), uniform `401` for missing/unknown/expired/revoked, token ID (never the secret) in the audit log and on completions |
| Prompt injection and over-reach through the MCP server | All names and text fields (household and chore names, notes, completion notes, repeat text) are household-typed text that reaches the model; the server cannot make a model ignore it, so it marks tool results as untrusted data in its instructions and tool descriptions and limits the blast radius instead: a token reaches only its bound households, only the tools its scopes allow (`tools/list` is per token, calls are checked again), never account, members, settings, channels, export or tokens, and no more than its owner's current role; every tool goes through the same store methods as the REST API, completions are recorded as `api_token` and audited, write tools take the per-user and per-household write buckets, and the endpoint can be switched off (`mcpEnabled`). Results carry no emails and no other member's details (ADR 0015) |
| DNS rebinding or cross-site calls to `/mcp` | The endpoint accepts a bearer token only (no cookies, nothing ambient to ride); a request whose `Origin` header is present and differs from `GUNKLY_BASE_URL` (else the Host) is refused with `403` before authentication; it is stateless (no session id to steal) and answers `404` when switched off |
| CSRF or cookie confusion with bearer requests | A bearer request is authenticated by the token alone and never reads or sets cookies; it needs no CSRF check because browsers do not attach the header on their own; a bad token is never rescued by a session cookie; the header is ignored on public routes |
| OAuth attack surface (ADR 0016) | Optional and off by default: while `oauth_enabled` is off every OAuth route and metadata document answers 404 before anything is read, nothing is advertised (not in `/api/v1/instance`, not in the `/mcp` challenge) and existing grants are dormant. Turning it on needs `GUNKLY_BASE_URL` to be https (or loopback http for development). Routes carry explicit policies (`oauthOnly`, `authClient`, `withFormCSRF`) checked at registration and by the route-table and OpenAPI fitness tests |
| Open dynamic client registration used for phishing (a hostile client named "Gunkly Backup") | Registration is anonymous by design (RFC 7591), so trust is not placed in the client: the consent page always labels the app "Unverified", shows its name escaped (html/template, `<` and quotes are text) and the host it will return to, and is reached only by a signed-in user; redirect URIs must be https or loopback http, with no fragment, userinfo, wildcard or odd host characters, and must match a registered URI exactly (a bad `client_id` or `redirect_uri` is an error page, never a redirect, so there is no open redirect); at most 5 URIs, 100-character names (never containing "gunkly" after Unicode folding, so no app can pass for the product), 10 registrations a minute per IP, 20 never-approved clients per registering IP (IPv6 as /64, the key stored but never logged), 1000 clients per instance with the oldest unused one evicted at the cap (so registration floods cannot lock real apps out), clients never approved purged after one hour; the return host is the most prominent line of the consent page and a host this user never approved before carries an extra warning; the user chooses the households and actions, least privilege by default (create is off unless the app asked for it) |
| Authorization code interception or injection | PKCE with S256 only and required (a missing, `plain` or wrong verifier is `invalid_grant`); codes are 256-bit, hashed at rest, single use (atomic mark-used), valid 60 seconds and bound to client, redirect URI and challenge; reuse revokes the whole grant; the redirect carries `iss` (RFC 9207) against mix-up; the post-consent redirect is done by the server (303) and the consent page names only the client's own origin in `form-action` |
| OAuth token theft or replay | Access tokens (`gko_`, 256 bits, hashed at rest) live one hour and are accepted only by `/mcp` (REST answers `401`, so a stolen token cannot reach account, members, settings or tokens); refresh tokens (`gkr_`) rotate on every use, expire after 30 idle days and 90 days overall, and presenting a rotated one revokes the grant (theft is detected at the next use by either side); `resource` must equal `<base>/mcp` (RFC 8707) and the audience is fixed; all tokens die with the grant, with a password change or second-factor removal, on account deletion, and `Disconnect` or RFC 7009 revocation; scopes, household binding, live role and rate limits are those of API tokens; token responses are `no-store` |
| Consent by a hijacked session (a stolen session cookie approving an attacker's app) | Approving needs a step-up, like token creation: the consent form asks for the password (and the authenticator, emailed or recovery code when the account has a second factor), or a user-verified passkey assertion, or a re-authentication at the identity provider for linked accounts, unless the session re-verified within 15 minutes; each is checked server-side with the same verifiers, per-account backoff and rate bucket as `POST /api/v1/session/step-up` (the passkey challenge is bound to the session and the consent page; the provider return must be the account's own subject with a fresh `auth_time`, via a sealed cookie of this session, and lands on a consent URL that is validated again), failures are audited and answered with one generic message; "Deny" needs nothing |
| Browser-based (cross-origin) abuse of the OAuth endpoints | No CORS headers: a web page cannot call registration, token or revocation from a browser, and browser-based MCP clients are therefore unsupported by design |
| CSRF or clickjacking of the consent form | The form post needs the `gunkly_csrf` cookie echoed as a hidden field plus the cross-site check (`Sec-Fetch-Site`/`Origin`); the page is `frame-ancestors 'none'` and `X-Frame-Options: DENY`; the only script on it is the same-origin `/oauth-consent.js` (no inline script; `script-src 'self'`), served only to accounts with a passkey, and the server trusts nothing it sets; `decision` defaults to deny; client endpoints read no cookies and so have nothing ambient to ride |
| Token creation by a hijacked session | Creation needs step-up (password or second factor within 15 minutes); a token cannot create or list tokens |
| Email-OTP brute force/replay | Single-use, 10-minute expiry, hashed with the challenge ID, 5 attempts per code then invalidated, per-account failure backoff, resends capped by the email limits |
| Account enumeration and mail bombing via reset/verify/email change/sign-up | Reset request always answers 202 and does lookup and send in the background for known and unknown logins; hosted sign-up answers 202 for taken addresses too (owner mailed a notice) and signs nobody in (self-hosted sign-up signs in at once and answers the generic `registration_failed` for a taken address or username, so it is an oracle for addresses there, accepted for username-and-password instances); email-change answers alike for taken addresses; per-IP, per-login and global email caps, a separate per-account cap for sign-in codes, and unauthenticated mail never touching the victim's account bucket (no lockout of their 2FA codes); up to 3 outstanding reset tokens so requests cannot invalidate the owner's link; tokens hashed, single use, expiring (1 h reset, 24 h verification) |
| SSRF via notification URL or push endpoint | Custom dialer with post-DNS IP check, private/loopback/link-local/CGNAT/metadata blocked, 3-redirect HTTPS-only cap, timeouts and body caps; CI tests every Shoutrrr service and Web Push against blocked ranges (Abuse resistance) |
| Malicious self-hosted service URL / redirect | Same guard on every hop; admin-controlled service allowlist; provider-host overrides rejected |
| Outgoing webhooks as an SSRF or internal-scan primitive (ADR 0017) | Optional and off by default (`webhooks_enabled`; routes `404` and nothing queued or sent while off). Owners only, step-up to create, 10 per household (`webhooks_per_household`), never API tokens. Every send goes through the egress guard (mandatory, forced on when hosted): post-DNS IP check on each connection, so loopback, private, link-local and metadata addresses are refused even behind DNS tricks; a stored target is re-validated at send time, so enabling the guard later also stops old loopback targets; https only unless the admin switched the guard off; **redirects are never followed** (a 3xx is a failure), 15 s timeout, response body read up to 4 KiB and discarded, so a target cannot return data or bounce the request. Errors shown to owners are fixed categories (no address, no resolver detail, no response text), so the log is not a port-scan oracle. The URL validator is fuzzed |
| Webhook secret or URL disclosure | URL and signing secret sealed with the instance key (associated data bound to the webhook id) and covered by `rotate-key`; the secret is returned once (create, rotate), the URL never (lists show the host); neither appears in logs, audit meta, the delivery log or payloads; payloads carry no emails, notes or links; rotating invalidates the old secret at once; deleting the household or webhook deletes the rows |
| Forged or replayed webhook deliveries | HMAC-SHA256 over `<timestamp>.<raw body>` with a per-webhook 256-bit secret; the timestamp is fresh on each attempt and documented with a 5-minute replay window; `Gunkly-Delivery` and the payload id allow de-duplication; verification code for shell, Python and Node is documented and tested |
| Webhook receiver outage turning into load or a retry storm | Asynchronous outbox in the scheduler with a lease, exponential backoff and 6 attempts per delivery, at most 1000 pending deliveries per webhook, auto-disable after 20 consecutive failures (audited, shown in the UI), log capped at 50 entries per webhook and purged with the delivery retention |
| Push endpoint abuse | Provider domain allowlist at registration, dial-time egress guard at send, per-user subscription cap, `404`/`410` pruning, endpoints never returned by the API, keys sealed at rest and covered by `rotate-key` |
| Metrics scraping and token guessing | `/metrics` exists only when `GUNKLY_METRICS_TOKEN` (16+ characters) is set; constant-time bearer compare, 30 requests/minute per IP; series carry no user or household labels and route patterns instead of paths |
| Update check leaking or abusing the instance | One GET of the public release document through the egress guard, generic User-Agent, no instance data, 12 h minimum interval, switchable off; the release text is stored length-capped and shown as plain text only |
| Link previews completing chores | GET shows confirmation only; POST with single-use hashed token completes; `Referrer-Policy: no-referrer`; tokens kept out of logs (Links without sign-in) |
| Mark-done token leak via provider | Single-use, max 7 days, scoped to occurrence and recipient/channel, invalidated on state-affecting changes, role downgrade, leave or password change; guests never get one; 5-minute single-use undo token |
| Calendar feed leak | Long random per-user-per-household token, names/areas/dates only, revocable and regenerable |
| Curious admin | Admin panel exposes no household content; admin password reset is disabled on hosted, refused for admin targets, revokes sessions and is visible in the target's own audit log (on self-hosted an admin can still take over a non-admin account, which is an accepted, now non-silent, trust-in-operator trade-off, ADR 0009); secrets encrypted at rest with versioned key and `gunkly rotate-key`; logs scrubbed of secrets |
| Authenticated abuse / data growth | Per-user and per-household write token buckets, areas-per-household cap, completion history retention, atomic households-per-user and invite-use limits |
| Spam relay / sign-up abuse | Limits service caps, SMTP caps, email verification and 2FA (hosted only; required for all household access in hosted mode, enforced in the router, including invited accounts and import), ALTCHA proof-of-work (a nuisance filter: HMAC-signed, expiring, marked used before any hashing; the per-IP sign-up cap is taken first), per-IP sign-up limit; in hosted mode unverified household-less accounts deleted after 7 days (email squatting) |
| Forged history via import | Imported completions carry source `import`; attribution to a named member only when the importer owns the target household; 20,000 completions per file; household row locked during merge on Postgres |
| XSS / injection | Strict CSP without inline scripts, server-side validation, output encoding, parameterised SQL only, link schemes limited to http/https |
| Clickjacking / MIME sniffing | Frame protection, `X-Content-Type-Options`, HSTS |
| Account lockout by third party | No hard lockouts; CLI recovery for admins; hosted has no manual 2FA reset (warned at setup) |
| Supply chain | Pinned dependencies, justification per dependency, govulncheck, gitleaks, CodeQL, license check, SBOM, cosign-signed images, Renovate/Dependabot |
| Data at rest on disk | SQLite database, -wal/-shm and backup/snapshot files are mode 0600; channel hints show only kind/host, never secret characters |
| Container compromise | Distroless, non-root, read-only rootfs, no shell, one port |
| Data loss / bad upgrade | Expand-and-contract migrations, pre-migration snapshots (SQLite), pre-deploy snapshot, canary with auto-rollback, tested restores |
| Duplicate or storm notifications | Unique delivery keys, scheduler lock, per-household and per-user caps, 24 h overdue cadence |
| Privacy/regulatory | Minimal data, no telemetry, export and delete, EU-only own infrastructure, breach procedure (72 h), processor agreements |
| Inactive account data retention | Optional inactivity warnings and deletion (idempotent, leader-only, admins exempt, 30 days notice); self-service account deletion in one transaction that strips audit rows of actor, IP and metadata; retention cleanup of audit (90 d) and delivery logs (30 d) |

## Out of scope / accepted risks

- Compromise of the host or database by the operator.
- Mailbox takeover defeating email-OTP and email reset (documented above).
- Content sent to third-party providers once delivered.
- Hosting infrastructure hardening, covered separately in operations documents.
- An external security review is required before the hosted service opens to the public.
